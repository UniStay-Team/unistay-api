# Репозитории UniStay

## Принятое решение и текущее состояние

Проект разделяется на три репозитория в общей организации UniStay-Team. Каждая часть имеет собственные main, ветки задач, Pull Request, зависимости, проверки и инструкции запуска.

| Целевой репозиторий | Содержимое | Основной ответственный |
| --- | --- | --- |
| `UniStay-Team/unistay-api` | C# / ASP.NET Core, EF Core, PostgreSQL, OpenAPI и серверные тесты | Алмас |
| `UniStay-Team/unistay-app` | Flutter-приложение студентов и арендодателей | Турар |
| `UniStay-Team/unistay-admin` | Angular-админка платформы | Талант |

Три приватных репозитория созданы с main. В unistay-app перенесены исходники Flutter с историей и авторством. API и admin содержат стартовую документацию; C# backend и Angular-приложение ещё предстоит написать. Код прежнего backend не переносится.

Репозитории принадлежат организации, всем троим нужен доступ к каждой части. Ответственность за компонент помогает координации и не даёт исключительного владения кодом. Фактические права GitHub проверяются отдельно; наличие участника в README не выдаёт доступ.

К предзащите 24 октября пользователь требует **три запускаемые основы уже на C#/Flutter/Angular**. Организация репозиториев и выделение Flutter выполнены; реализация и общая проверка D0 остаются частью P0. Полный функционал завершается после показа. D0 считается готовым, когда заявка из Flutter сохраняется в C# API/PostgreSQL и видна в Angular: [D01–D08 и этапы D0/V1](project-plan.md).

## Содержимое репозиториев

| Текущая часть | Целевое размещение | Правило |
| --- | --- | --- |
| Flutter | Корень `unistay-app` | История сохранена; `pubspec.yaml`, `lib/`, `test/`, `android/` и `ios/` находятся в корне |
| Прежний сервер | Только отдельная резервная копия | В новые репозитории не переносится; новый API создаётся по ТЗ |
| Новый C# backend | `unistay-api` | Один API, одна PostgreSQL; проекты UniStay.Api, UniStay.Application, UniStay.Core и тесты. Их точные пути фиксируются при создании solution |
| Новая Angular-панель | Корень `unistay-admin` | Здесь находятся её package.json, исходники, конфигурация и проверки. Пользовательские кабинеты остаются во Flutter |
| Общие правила | `AGENTS.md` в корне каждого репозитория | Одинаковый текст общих правил, применяемый к соответствующему стеку |
| Документация API | `unistay-api` | Единственный источник контрактов; клиенты ссылаются на согласованную версию |
| README и команды запуска | Каждый репозиторий | Команды работают из его корня и не предполагают наличие соседних папок прежнего монорепозитория |

Работа ведётся в трёх самостоятельных репозиториях. Старый общий репозиторий выведен из рабочего процесса; локальная резервная копия не является зависимостью.

## Общий Git-порядок

Полная последовательность команд приведена в [AGENTS.md](../AGENTS.md). Она применяется отдельно к каждому репозиторию:

1. Проверить рабочую папку, origin, ветку и незавершённые изменения.
2. Получить свежую origin/main и создать ветку конкретной задачи.
3. Внести изменения, выполнить проверки своего компонента и проверить diff.
4. При поручении создать точечный коммит и отправить только ветку задачи.
5. При поручении на PR открыть его в main того же репозитория; получить ревью другого участника.

Одинаковые имена веток в разных репозиториях не объединяют их. Один PR не может включать изменения сразу трёх репозиториев.

При изменении общего сценария создаются связанные PR только в затронутых репозиториях. Их описания содержат ссылки друг на друга, версию контракта, порядок переключения и результаты интеграционной проверки. До создания PR достаточно указать репозиторий и ветку зависимого изменения.

## Согласование API

- Контракт, DTO, ошибки, пагинация, права и OpenAPI поддерживаются в `unistay-api`. Путь к файлу схемы и команда его генерации фиксируются при реализации.
- Flutter и Angular используют один сервер, а не собственные базы или отдельные backend.
- Изменение формата ответа или endpoint требует проверки всех потребителей. Клиентские PR ссылаются на commit или версию схемы, с которой они проверены.
- По возможности сначала добавляйте совместимое расширение API, затем обновляйте клиентов. Удаление старого поля или endpoint выполняется после согласованного перехода.
- Проверка API отдельно от клиентов не подтверждает совместимость. Для общего сценария зафиксируйте версии сервера и клиентов, на которых он проверен.
- На промежуточный D0: admin-вход и чтение пользователей, объявлений и заявок, без PATCH.
- Объём полной версии админки подтверждён пользователем 23 октября: просмотр пользователей, изменение имени, блокировка/разблокировка и редактирование профилей; объявления, фото, заявки и события — чтение. Без удаления аккаунтов и назначения прав. Реализация следует [admin-api-v1.md](admin-api-v1.md); дополнительные полномочия не следуют из разделения репозиториев.

## Как поддерживать одинаковый AGENTS.md

Исходная общая версия поддерживается в `unistay-api/AGENTS.md`, идентичные копии — в корнях `unistay-app` и `unistay-admin`.

При изменении общих правил:

1. Подготовить изменение в unistay-api и явно отметить затронутые правила.
2. Перенести тот же текст связанными PR в остальные два репозитория.
3. Сверить содержимое файлов; в описаниях PR указать исходный commit общих правил.
4. Считать синхронизацию завершённой после обновления всех трёх копий.

GitHub-организация сама не распространяет AGENTS.md между репозиториями. Локально отредактированная пересланная копия не становится новой общей версией автоматически.

Общие правила содержат разделы для всех стеков. Агент применяет проверки своей части; пути и команды относятся к корню своего репозитория. Дополнительные инструкции конкретного компонента допускаются во вложенном AGENTS.md, если не меняют общие правила Git.

Поддерживайте связанные документы `docs/repositories.md`, `docs/implementation-guide.md`, `docs/project-plan.md` и `docs/admin-api-v1.md`, `docs/public-api-v1.md` и `docs/public-api-baseline.yaml`, чтобы ссылки из общего файла оставались рабочими. README каждого репозитория описывает именно его код и реальные команды.
