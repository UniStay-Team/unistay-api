## 1. Общая система

Flutter обслуживает студентов и владельцев жилья. Angular предназначен только для администратора. Оба клиента используют один ASP.NET Core API и один контракт /api/v1/. PostgreSQL доступна только серверу; файлы фотографий хранятся в постоянном томе.

К предзащите обязательна связка: каталог во Flutter → создание pending-заявки через C# → та же запись в таблице Angular. Готовность подтверждается Q01–Q06. Остальной объём завершается по плану V1.

## 2. C# API

| Проект | Ответственность |
| --- | --- |
| UniStay.Api | HTTP endpoints, DTO, сериализация, аутентификация, проверка доступа, OpenAPI, конфигурация |
| UniStay.Application | Сервисы аккаунтов, жилья, заявок и административных изменений |
| UniStay.Core | Сущности, EF Core DbContext, связи, ограничения и миграции |
| Тестовый проект | Проверка HTTP-контракта, прав и бизнес-операций; интеграционные сценарии PostgreSQL |

Это логическая структура. Точные пути solution/project фиксируются в README при создании файлов. Один API достаточен; дополнительные сервисы и универсальные обёртки добавляются только при конкретной необходимости.

Контроллер принимает DTO, получает пользователя из проверенной сессии, вызывает сервис и возвращает согласованный результат. Роль или owner_id из запроса не заменяют проверку сервером. Сервис выполняет бизнес-проверки и транзакцию.

Для чтения применять проекции в DTO и AsNoTracking; фильтрация и пагинация выполняются на сервере. Сортировка имеет устойчивый вторичный ключ id. Асинхронные операции принимают CancellationToken.

Заявка pending не занимает место. Принятие в V1 выполняется с проверкой вместимости и транзакционной блокировкой; уникальные ограничения защищают активную заявку и единственное принятое место студента. EF InMemory и SQLite не доказывают корректность блокировок PostgreSQL.

Авторизация сохраняет непрозрачную Bearer-сессию: случайный токен, хеш на сервере, срок 24 часа и отзыв при выходе/блокировке. Пароль хешируется стандартным механизмом ASP.NET. Нельзя отправлять клиенту сущность EF с паролем, хешем или служебными токенами.

## 3. Flutter

Используется существующий клиент UniStay с его ApiClient, AppState и навигацией. До переноса нового поведения нужно проверить соответствующий текущий экран и тест.

- D0: вход, каталог, карточка, подача заявки, «Мои заявки».
- V1: регистрация и почта, профиль, соседи и совместимость, полный кабинет владельца, фотографии и переходы заявок.
- Серверный результат определяет состояние. После успешной операции обновляются затронутые данные.
- При 401 очищается приватное состояние; при 409 обновляются актуальные данные и показывается причина конфликта.
- После сетевого сбоя при POST сначала выясняется результат по списку; повторное создание автоматически не отправляется.
- Кнопка сохранения блокируется на время запроса, введённые поля сохраняются при ошибке.
- Галерея получает photos[].image, использует общий преобразователь URL, имеет перелистывание, увеличение, loading/error/empty.
- Формы владельца проверяют поля жилья, но сервер повторяет проверки независимо от клиента.
- Токен отправляется только настроенному API. API_BASE_URL — корень сервера без /api/v1; при тестировании проверяется также сохранённая настройка.

## 4. Angular

Standalone-компоненты объединяются по функциям: auth, users, listings, applications; V1 добавляет profiles, photos и application-events. Общая оболочка содержит меню, текущего администратора и выход.

D0 реализует login, проверку admin/me и три таблицы только для чтения. Фикстуры допустимы при разработке интерфейса, но отключаются в проверяемой интеграции.

Для V1:

- Список пользователей поддерживает серверные фильтры и страницы, просмотр профиля и разрешённое редактирование.
- Форма пользователя меняет только name/is_active; форма профиля — поля из admin-api-v1.md.
- Блокировка требует диалога с именем выбранного пользователя и ожидания ответа сервера.
- Объявления, фото, заявки и события доступны только для чтения.
- Каждый экран различает загрузку, пустой ответ, сетевой сбой, отсутствие сессии и отказ в доступе.
- Guard управляет навигацией; сервер проверяет право на каждом запросе.
- Interceptor прикрепляет токен только к настроенному API. В D0/V1 токен хранится в памяти, перезагрузка страницы требует нового входа.
- Кнопки без реализации не выглядят как работающие операции.

## 5. Общий контракт

| Область | Правило |
| --- | --- |
| Маршруты | /api/v1/, согласованные method/path и завершающий slash |
| Имена полей | snake_case |
| ID | Положительные целые JSON-числа |
| Сессия | Login возвращает token, expires_at, user |
| Пользователь | Бизнес-роль student/landlord; право администратора проверяется отдельно |
| Списки | count, next, previous, results; 20 записей на страницу |
| Деньги | Decimal в БД, строки с двумя десятичными знаками в JSON |
| Время | UTC, ISO 8601 с Z; дата доступности отдельно YYYY-MM-DD или null |
| Ошибки | error.status и error.details; значения и HTTP-код согласованы |
| Фото V1 | Multipart image/caption; ответ id/image/caption; URL доступен клиенту |

Фото V1: до 10 на объявление, до 5 MiB на файл, до 20 мегапикселей; JPEG/PNG/WebP. Сервер проверяет содержимое, удаляет EXIF и перекодирует JPEG. Загрузка и удаление проверяют владельца; анонимного Upload нет.

Обычные и административные DTO различаются намеренно: например, публичный Listing содержит owner, а AdminListing — owner_id. Точный адрес маскируется в публичном ответе и выдаётся через защищённый admin endpoint. Не унифицировать эти структуры ценой нарушения контракта.

## 6. Порядок совместной реализации

1. Алмас фиксирует минимальную OpenAPI и примеры успешного ответа/ошибок; Турар и Талант сверяют их со своими экранами.
2. Все трое создают запускаемые основы и README; выбранные версии зависимостей фиксируются.
3. API реализует вход/каталог; Flutter проверяет реальное чтение.
4. API реализует заявку и admin-списки; оба клиента проходят общий сценарий с одним ID.
5. Q01–Q06 подтверждают D0; в V1 команда расширяет контракт и выполняет T01–T12.
6. Связанные изменения оформляются в ветках соответствующих репозиториев, с указанием версии контракта и результатов проверки.

README каждого репозитория содержит реальные команды установки, сборки, запуска и проверки, пример настроек, разделы «Работает в D0» и «Остаётся до V1». Команды не зависят от персонального пути участника или неописанного соседнего каталога. Секреты, БД и сборочные артефакты в Git не включаются.

Актуальная OpenAPI хранится в API-репозитории; клиенты ссылаются на её commit. Выпуск фиксирует commit всех трёх компонентов и фактические результаты проверок.
