# UniStay — план проекта и техническое задание

Версия 1.1 · 23 октября 2026 года · часовой пояс Asia/Qyzylorda.

**Статус:** план реализации. Репозитории разделены: Flutter перенесён с историей, API и админка получили стартовую документацию. C# backend пишется с нуля по ТЗ; Angular ещё предстоит реализовать. Создание репозиториев не означает готовность D0. Предзащита — **24 октября 2026 года**; дата окончательной защиты ещё не задана. Пользователь выбрал демонстрацию на тестовых данных, без публичного запуска.

## 1. Краткое резюме и результат

UniStay помогает студенту найти отдельное место в квартире, увидеть разрешённые профили будущих соседей, оценить совпадение бытовых привычек и подать заявку. Владелец размещает жильё и принимает решения по заявкам. Администратор управляет ограниченным набором данных пользователей и просматривает состояние платформы.

Два разных результата:

- **D0 — предзащита 24 октября:** три отдельных запускаемых репозитория уже на целевом стеке. Сквозной путь: Flutter показывает жильё из C# API → студент отправляет заявку → Angular показывает ту же запись из PostgreSQL. Комиссия видит архитектуру, реальный вклад каждого и план завершения.
- **V1 — полная дипломная версия:** C# / ASP.NET Core + EF Core + PostgreSQL, Flutter для студентов и владельцев, Angular-админка с подтверждённым объёмом, три репозитория и комплект проверок/документов.

Пользователь уточнил: все три репозитория должны иметь работающую основу уже к предзащите. Поэтому создание C# API, Angular и выделение Flutter входят в D0. Пустые репозитории, три независимых макета или Django под видом C# не соответствуют результату. Старый серверный код не переносится. Публичный контракт сохранён в документации; реализация C# создаётся заново. Резерв исходного репозитория хранится отдельно и не требуется для разработки.

В V1 арендуется отдельное место. Принятая заявка отражает согласие владельца и учёт вместимости; она не является оплатой, договором или доказательством фактического заселения. Подбор соседей — объяснимая эвристика, а не обученная модель.

D0 сознательно откладывает регистрацию/письма, редактирование профиля, создание жилья и загрузку фото из интерфейса, принятие/отклонение/отмену заявки, подбор соседей и административные изменения до V1. Используются заранее созданные тестовые аккаунты и объявления; это явно сообщается на защите. Указанные возможности остаются требованиями V1, а не исчезают из диплома.

Минимальный контракт D0: POST /api/v1/auth/login/ и auth/logout/; GET /api/v1/me/, me/profile/, listings/, listings/{id}/; GET/POST /api/v1/applications/ и GET applications/{id}/; GET /api/v1/admin/me/, admin/users/, admin/listings/, admin/applications/; GET /health/, /api/schema/, /api/docs/. POST заявки принимает listing_id (положительное целое) и message (необязательная строка, до 1000 символов), возвращает 201 и созданный Application. Обычный GET заявок ограничен собственными заявками студента/объектами владельца; admin GET имеет отдельные DTO.

Для D0 сохраняются правила F08: published, свободное место, заполненный профиль, ≤5 pending, одна активная заявка на объект, ≤1 accepted на студента. Проверки и вставка выполняются в транзакции с блокировками. При неизвестном исходе запроса клиент обновляет список, а не повторяет POST автоматически.

Формы ответов обычного API сверяются с [публичным контрактом](public-api-v1.md) и [OpenAPI baseline](public-api-baseline.yaml), административные списки — с [admin-api-v1.md](admin-api-v1.md). В D0 permissions содержит только users.read, listings.read, applications.read. Не реализованные PATCH/другие разделы не обещаются OpenAPI и не показываются активными в панели; полной административной спецификации соответствуют позже в P4. Все существующие маршруты admin сначала проверяют доступ.

Демонабор: 2 студента с заполненными профилями, 1 владелец, 1 отдельный администратор, 3 опубликованных объявления вместимостью 2/3/4 с одним локальным разрешённым фото каждое; перед каждым прогоном нет заявок и occupied=0. Первый студент создаёт pending, второй используется для проверки чужого доступа. Демо-пароли задаются локально; скрипт сброса требует явно выбранной demo-среды и не работает с другими БД. В D0 нет принятой заявки, поэтому никаких заявлений о проверенной конкуренции за последнее принятое место.

### V1: входит

- Аккаунты двух бизнес-ролей, сессии, подтверждение email и восстановление доступа через тестовый почтовый приёмник.
- Профили, согласие на показ соседям, каталог и фильтры, объявления, фото, дата доступности, учёт отдельных мест.
- Заявки, принятие/отклонение, отмена, история, защита от конкурентного занятия мест.
- Flutter-кабинеты студента и владельца, включая регистрацию владельца и формы объявлений.
- Angular: пользователи — просмотр, имя, блокировка/разблокировка; профили — редактирование; объявления, фото, заявки и события — только чтение.
- API-документация, тесты, демонабор, развёртывание, резервное копирование, инструкция оператора и материалы защиты.

### Не входит в V1

Оплата, договор и электронная подпись, бронирование квартиры целиком, отдельное подтверждение всей группы, временное удержание места с таймером, карты/маршруты, чат, отзывы и рейтинг, проверка документов студента/собственника, push, ML, публичный маркетплейс и публикация в App Store/Google Play.

Нет второго пользовательского сайта: Flutter web — запуск того же клиента для демонстрации. Нет микросервисов, Redis или очереди ради будущего масштаба. Для демонстрации не нужен платный сервер или реальный SMTP. Публичная эксплуатация — отдельный будущий проект с новыми критериями.

Приоритеты старого двухдневного web-плана заменены последними решениями пользователя. Упоминания отзывов, квартиры целиком и новых ролей в старых обоснованиях нужно согласовать с руководителем, а не автоматически включать в реализацию.

### 4.2. Состояния и обязательные инварианты

Заявка: pending → accepted/rejected/cancelled; accepted → cancelled. rejected/cancelled терминальны; новая заявка создаётся отдельно. Первый accepted занимает одно место. Объявление: draft/published/archived; административный API не меняет эти статусы.

Всегда: 0 ≤ occupied ≤ capacity; capacity от 1 до 6; available = capacity − occupied; group_ready = available == 0. occupied считается по accepted, а не по количеству отправленных заявок. Блокировка пользователя не освобождает место и не удаляет историю.

На PostgreSQL транзакции блокируют связанные записи в едином порядке «студент → объявление → заявка». Частичные уникальные ограничения защищают единственное accepted у студента и единственную активную заявку на объект. Проверка capacity и запись статуса происходят в одной транзакции с блокировкой объявления. Проверка в клиенте не заменяет эти ограничения.

### 4.4. Основной API и данные

ТЗ задаёт поведение нового API. Поля запросов и ответов зафиксированы в public-api-v1.md и public-api-baseline.yaml; доступ к прежнему серверному коду не требуется. Версионируемая OpenAPI-схема целевого API хранится в `unistay-api/docs/openapi.yaml`; это будущий выход генерации, сейчас не созданный этим планом.

| Группа | Основные endpoints |
| --- | --- |
| Аккаунт | POST auth/register/, auth/login/, auth/logout/, auth/verify-email/, auth/resend-verification/, auth/password-reset/, auth/password-reset/confirm/ |
| Профиль | GET me/; GET/PATCH me/profile/ |
| Объявления | GET/POST listings/; GET/PATCH/DELETE listings/{id}/; GET listings/mine/; GET listings/{id}/group/ |
| Фотографии | POST listings/{id}/photos/ с image/caption; DELETE photos/{id}/ |
| Заявки | GET/POST applications/; GET applications/{id}/; POST applications/{id}/accept/, reject/, cancel/ |
| Администрирование | Отдельное пространство /api/v1/admin/ по [точному контракту](admin-api-v1.md) |
| Диагностика | /health/, /api/schema/, /api/docs/ |

Пути первых пяти строк идут после /api/v1/. DELETE объявления означает архивирование. Списки используют count/next/previous/results. Ошибка — error.status/details; 400 — валидация, 401 — сессия, 403 — право/подтверждение почты, 404 — объект отсутствует или не доступен владельцу, 409 — конфликт, 429 — ограничение частоты. Регистрация возвращает пользователя, вход — token/expires_at/user.

Модель данных: User → Profile (1:1); User(owner) → Listing → ListingPhoto; User(student) + Listing → Application → ApplicationEvent; User → ApiSession; администратор → AdminAuditEvent. Фото хранятся в отдельном постоянном томе, в БД — ссылка и метаданные. Деньги — decimal, даты событий — UTC, дата доступности — дата без времени.

## 5. Решение и взаимодействие частей

```text
Студент / владелец
        │
        ▼
unistay-app (Flutter) ───────┐
                            │ HTTP JSON, /api/v1/
Администратор               ▼
        │              unistay-api (ASP.NET Core)
        ▼                   │
unistay-admin (Angular) ─────┤
                            ├── Application: бизнес-операции
                            ├── Core / EF Core → PostgreSQL
                            ├── постоянный том фотографий
                            └── тестовый почтовый приёмник
```

Один API и одна БД. Angular не подключается к PostgreSQL. Flutter не хранит вторую базу объявлений. Состояние на клиентах — отображение ответа сервера, после операции оно обновляется из подтверждённого результата.

Для D0 рекомендуемые локальные адреса: API http://127.0.0.1:8000, Flutter web http://127.0.0.1:3000, Angular http://127.0.0.1:4200. Это настройки будущего стенда, а не проверенные сейчас процессы. CORS разрешает только настроенные адреса двух клиентов; порты подтверждаются при запуске. API_BASE_URL во Flutter — корень сервера без /api/v1; сохранённый ранее адрес нужно проверить, поскольку он имеет приоритет над параметром сборки. Для Android-эмулятора адрес компьютера — 10.0.2.2; перенос показа на устройство требует отдельной сетевой проверки. D0 по умолчанию показывается на одном ноутбуке через Flutter web; мобильная Android-проверка остаётся обязательной для V1.

C#-решение: UniStay.Api (HTTP, DTO, auth, OpenAPI), UniStay.Application (сервисы), UniStay.Core (сущности, DbContext, миграции), тестовый проект. Слои имеют отдельные обязанности; для этого объёма отдельные микросервисы не нужны.

Для первого переноса рекомендуется сохранить непрозрачные сессии: случайный токен, хеш на сервере, срок и отзыв. Пароли обрабатываются стандартным ASP.NET-механизмом. JWT не требуется для сохранения согласованного протокола сессий. Это технический default плана, а не утверждение о готовом коде.

Основной путь: владелец создаёт draft → загружает фото → публикует → студент фильтрует каталог → смотрит условия/соседей → отправляет pending → владелец принимает → сервер атомарно занимает место и добавляет событие → клиент показывает accepted и доступный адрес → студент отменяет → место освобождается.

Администратор входит обычной сессией, проверяет /admin/me/, открывает пользователя, меняет разрешённые поля; сервер сохраняет аудит. Просмотр заявки не даёт права принять её от имени владельца.

## 11. Выпуск, передача и эксплуатация

Выпуск V1 — демонстрационный комплект, не публичный сервис. Основной стенд локальный: API, PostgreSQL, media, тестовая почта; Angular и Flutter подключаются к нему. На удалённом учебном стенде потребуется HTTPS и отдельная конфигурация, но его отсутствие не блокирует выбранный локальный результат.

Комплект: исходники/версии трёх репозиториев, README каждого, OpenAPI, ER/архитектура, сценарий показа, демоданные и их происхождение, инструкция запуска/сброса/копирования/восстановления, тестовый отчёт, перечень ограничений и подтверждённые индивидуальные вклады.

`release-manifest.md` в API-репозитории должен перечислять commit каждого компонента, версии runtime и схемы, дату тестов и известные ограничения. Этот файл создаётся при выпуске, а не задним числом как доказательство уже готовой версии.

Передача: Алмас показывает запуск и восстановление Турару; Турар показывает студенческий/владельческий путь Таланту; Талант показывает разрешённые действия админки Алмасу. На обучение — по 30 минут, затем каждый повторяет чужой сценарий по инструкции.

Эксплуатация до полной защиты:

- Перед каждой сессией: /health/, свободное место, запуск БД/media, тестовый вход.
- После каждой законченной сессии разработки с изменёнными демоданными: копия БД и media; хранить 7 последних копий в локальном закрытом каталоге вне Git.
- Раз в неделю: восстановить одну копию на отдельном демо-стенде и пройти основной путь.
- Логи: request_id, endpoint, status, duration и безопасная причина ошибки; хранить 7 дней, без токенов/паролей/ссылок восстановления.
- Проблему заводить в общий backlog в день обнаружения. S1/S2 блокируют очередной показ; владелец компонента исправляет и второй участник перепроверяет.
- Обновления зависимостей: один согласованный слот в неделю после тестов; за 24 часа до защиты обновления запрещены.
- Стенд запускается для разработки/демо и выключается после завершения; SLA 24/7 не обещается.

Публичный запуск потребует отдельного согласования реальных данных, приватности, поддержки, модерации, реальной почты, размещения, резервирования и распространения приложения. Эти работы не включены скрыто в критерии дипломной V1.

## 13. Факты, допущения и решения

### Подтверждено пользователем

Три участника и распределение компонентов; организация UniStay-Team; три отдельных репозитория; C# backend, Flutter как основной интерфейс, Angular как админка; демонстрация на тестовых данных; предзащита завтра, 24 октября, с работающей основой всех трёх репозиториев; время на полный проект ещё есть; объём админки F12–F15 подтверждён. ### Установлено по доступным файлам

В unistay-api и unistay-admin находятся ТЗ, контракты и правила для начала разработки. Фактические проверки переноса записаны в docs/transfer-validation.md приложения; полноценная C# интеграция ещё не проверялась.
