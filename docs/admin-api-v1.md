# Административный API UniStay v1 — техническое задание

Дата: 23 октября 2026 года. Пользователь подтвердил объём: пользователи — просмотр, имя и блокировка; профили — редактирование; объявления, фотографии, заявки и история — просмотр. Удаление аккаунтов и выдача административных прав через панель исключены.

Это спецификация будущего C# API, а не описание уже реализованных endpoints. Числа, поля и правила ниже — конкретизация для реализации. Административная часть пишется с нуля в ASP.NET Core; спецификация доступна команде без старого сервера. Связанный [план и критерии приёмки](project-plan.md), требования F12–F16.

## 1. Доступ и сессия

- Префикс: `/api/v1/admin/`; канонические пути заканчиваются `/`.
- Общий вход: `POST /api/v1/auth/login/` с `email/password`. Ответ сохраняет `token/expires_at/user`. Для v1 рекомендуется сохранить непрозрачную Bearer-сессию на 24 часа, чтобы не менять одновременно backend и клиентский протокол.
- Каждый административный запрос проверяет сессию, активность аккаунта, подтверждённую почту и серверное право администратора. Роли `student` и `landlord` этого права не дают.
- Административное право назначается только локальной служебной процедурой/демо-seed. Публичная регистрация и PATCH пользователя его не принимают.
- `GET /api/v1/admin/me/` проверяет доступ Angular. Ответ: `id, email, name, permissions`. ID — положительное целое JSON-число; email/name — строки; permissions — массив строк.
- Для v1 один административный набор: `users.read`, `users.update`, `profiles.read`, `profiles.update`, `listings.read`, `photos.read`, `applications.read`, `application_events.read`. Это описание возможностей панели; сервер проверяет право на каждом endpoint.
- Текущий публичный `GET /api/v1/me/` не требует изменения ради Angular. Поля текущего пользователя и административные полномочия не смешиваются.
- Angular хранит токен в памяти; перезагрузка страницы требует повторного входа. Interceptor отправляет токен только настроенному API. После logout/401 очищаются пользователь, таблицы и выбранные записи.
- `401` — отсутствующая, отозванная, просроченная сессия или заблокированный аккаунт; `403` — аутентифицированный пользователь без административного доступа/подтверждённой почты. Сбой сети не выдаётся за отказ в доступе.

## 2. Маршруты

Все пути в таблице указаны после `/api/v1/admin/`. У коллекций и деталей GET возвращает 200.

| Method | Path | Результат / разрешённое изменение |
| --- | --- | --- |
| GET | `me/` | Текущий администратор и capabilities через permissions |
| GET | `users/` | Страница пользователей |
| GET | `users/{id}/` | AdminUser |
| PATCH | `users/{id}/` | Только name и is_active; ответ AdminUser, 200 |
| GET | `users/{id}/profile/` | AdminProfile; id в URL — ID пользователя |
| PATCH | `users/{id}/profile/` | Только university, bio, schedule, smoking, cleanliness; ответ AdminProfile, 200 |
| GET | `listings/` | Страница объявлений всех статусов |
| GET | `listings/{id}/` | AdminListing |
| GET | `photos/` | Страница фотографий |
| GET | `photos/{id}/` | AdminPhoto |
| GET | `applications/` | Страница заявок |
| GET | `applications/{id}/` | AdminApplication |
| GET | `application-events/` | Страница переходов статусов заявок |
| GET | `application-events/{id}/` | AdminApplicationEvent |

POST, PUT и DELETE к перечисленным административным ресурсам не реализуются; для существующего маршрута возвращается 405 после проверки доступа. Отсутствующий маршрут возвращает 404. HEAD/OPTIONS допустимы и не меняют данные. Административных accept/reject/cancel/publish/upload нет.

Студент и владелец продолжают выполнять свои операции через обычный API. Наличие административных прав не позволяет обходить бизнес-проверки обычных endpoints.

## 3. Общие правила данных и пагинация

- JSON-поля в snake_case; ID и ссылки на сущности — положительные целые числа, совместимые с существующим Flutter. Не заменять их строковыми UUID при переносе без изменения общего контракта.
- Денежные суммы — строки с двумя десятичными знаками; timestamps — ISO 8601 в UTC с Z; `move_in_date` — YYYY-MM-DD или null.
- Пагинация: `page`, целое от 1; размер страницы фиксирован — 20. `page_size` в v1 не поддерживается.
- Ответ страницы: `count` — количество после фильтров; `next/previous` — URL следующей/предыдущей страницы с текущими фильтрами либо null; `results` — массив DTO.
- Пустая первая страница: 200, count=0 и results=[]. Несуществующая положительная страница: 404. Некорректный page/фильтр: 400. Неизвестные query-параметры: 400.
- Набор всех полей DTO одинаков для коллекции и детали. Профиль и история загружаются отдельными запросами, а не вкладываются в каждую строку списка.
- Все перечисленные поля ответа присутствуют; null разрешён только там, где это указано.

Пример синтетической страницы:

```json
{
  "count": 1,
  "next": null,
  "previous": null,
  "results": [
    {
      "id": 101,
      "email": "student1@example.test",
      "name": "Тестовый студент",
      "role": "student",
      "email_verified": true,
      "is_active": true,
      "is_admin": false,
      "date_joined": "2026-10-23T06:00:00Z"
    }
  ]
}
```

## 4. DTO и фильтры

| DTO | Поля ответа |
| --- | --- |
| AdminUser | id, email, name, role, email_verified, is_active, is_admin, date_joined |
| AdminProfile | user_id, university, bio, schedule, smoking, cleanliness, share_with_group |
| AdminListing | id, owner_id, owner_name, title, description, city, district, address, university, price, deposit, utilities_included, capacity, move_in_date, status, occupied, available, group_ready, created_at, updated_at |
| AdminPhoto | id, listing_id, image, caption, created_at |
| AdminApplication | id, student_id, student_name, listing_id, listing_title, status, message, created_at, updated_at |
| AdminApplicationEvent | id, application_id, actor_id, from_status, to_status, created_at |

Типы: все id/count/capacity/occupied/available — целые числа; is_*, email_verified, utilities_included, group_ready, share_with_group — boolean. Остальные поля — строки, кроме smoking (boolean или null) и move_in_date (строка или null). Поля created_at/updated_at/date_joined — timestamps указанного формата.

- role: student или landlord. is_admin — отдельное серверное право; поле только для чтения.
- Listing.status: draft, published, archived.
- Application.status/to_status: pending, accepted, rejected, cancelled. from_status дополнительно допускает пустую строку для первого события.
- AdminListing.address доступен администратору полностью. Это отдельный защищённый DTO; публичный Listing сохраняет маскирование адреса.
- AdminPhoto.image — URL, который понимает настроенный клиент; внутренний путь файловой системы не выдаётся.
- Нет паролей, хешей, сессионных токенов, ключей восстановления, групп Identity и произвольных дополнительных полей.

| Коллекция | Фильтры помимо page | Фиксированный порядок |
| --- | --- | --- |
| users | search по email/name без учёта регистра; role; is_active; email_verified | id по возрастанию |
| listings | search по title/description; city без учёта регистра; owner_id; status | created_at по убыванию, затем id по убыванию |
| photos | listing_id | id по возрастанию |
| applications | student_id; listing_id; status | created_at по убыванию, затем id по убыванию |
| application-events | application_id; actor_id | created_at по убыванию, затем id по убыванию |

Фильтры комбинируются через AND; внутри search несколько полей объединяются OR. Boolean в query — true/false. Пустой search/city означает отсутствие этого фильтра; ID должны быть положительными. Все коллекции включают связанные данные заблокированных пользователей, чтобы администратор мог исследовать состояние.

## 5. Изменение пользователя

PATCH — обычный частичный JSON-объект, не формат JSON Patch. Пропущенное поле сохраняет значение. Неизвестное или доступное только для чтения поле вызывает 400; запрос применяется целиком либо не применяется.

- name: строка после trim, 1–120 символов.
- is_active: boolean. false блокирует, true снимает блокировку обычного пользователя.
- email, role, email_verified, is_admin и date_joined не меняются через этот endpoint.
- Блокировка/разблокировка административного аккаунта через панель запрещена: 409. Это включает собственный аккаунт администратора.
- Блокировка отзывает все действующие сессии пользователя в той же транзакции. Следующий защищённый запрос и новая попытка входа отклоняются. При разблокировке старые токены не оживают, нужен новый вход.
- Блокировка не отменяет заявки, не освобождает принятое место и не архивирует объявления. Эти данные остаются в истории; панель v1 не решает вопросы выселения и модерации объявления.
- Повтор PATCH с теми же значениями возвращает 200 без повторного изменения или лишней записи аудита.
- Пустой PATCH без разрешённых полей: 400. Смена имени и is_active одним запросом атомарна.

Пример:

```json
{"name":"Тестовый студент 2","is_active":false}
```

## 6. Изменение профиля

| Поле | Ограничение PATCH |
| --- | --- |
| university | Строка, максимум 160 символов; пустая строка разрешена |
| bio | Строка, максимум 1000 символов; пустая строка разрешена |
| schedule | early, late или пустая строка |
| smoking | true, false или null |
| cleanliness | tidy, relaxed или пустая строка |

user_id и share_with_group доступны только для чтения. Согласие на показ профиля меняет сам пользователь через обычный профильный API; администратор не даёт согласие за него.

Администратор может просмотреть профиль при share_with_group=false. Это не делает профиль видимым другим студентам. Очистка обязательных для новой заявки полей не отменяет существующие заявки, но новая заявка проходит обычную проверку заполненности.

Профиль создаётся вместе с аккаунтом. Пользователь/профиль не найден — 404; GET не создаёт записи. Пустой PATCH, неизвестные поля и неправильные значения — 400. Отсутствующие поля не затираются.

## 7. Ошибки и аудит

Формат ошибки сохраняется совместимым с текущим API:

```json
{"error":{"status":400,"details":{"name":["Имя должно содержать от 1 до 120 символов."]}}}
```

Для 401/403/404/405/409/429/500 details может быть строкой; для ошибок полей — объектом со списками сообщений. 500 содержит общую формулировку, без stack trace и внутренних путей. 429 содержит Retry-After. Лимиты авторизации и email сохраняются общими для API.

Каждое фактическое административное изменение записывается атомарно в AdminAuditEvent: id, actor_id, target_user_id, action (user.updated/profile.updated), changed_fields, before, after, created_at, request_id. before/after содержат только изменённые разрешённые поля. Пароли и токены не попадают в аудит. Эта техническая история отдельно от ApplicationEvent, не редактируется и не имеет нового UI/endpoint в v1.

## 8. Приёмка

- T05: обычные студент и владелец не получают данные ни одного admin endpoint; прямой HTTP-запрос проверяется независимо от Angular guard.
- T07: администратор получает страницы и детали; фильтры, стабильный порядок и границы страниц соответствуют контракту.
- T07: разрешённые PATCH сохраняются и отображаются после обновления; запрещённые поля возвращают 400 и не меняют ни одно поле.
- T07: блокировка отзывает сессии; повторный login заблокирован; после разблокировки нужен новый login. Число принятых мест не меняется.
- T07: невозможно блокировать администратора, удалить аккаунт, выдать права или изменить email/роль через панель.
- T07: share_with_group не меняется администратором; прямой запрос не обходит ограничение.
- T07: любое изменение объявлений/фото/заявок/событий через admin API отвергается, а данные остаются прежними.
- T07: реальное изменение создаёт ровно одну запись аудита; повтор без изменения — ни одной.
- T11: Flutter продолжает работать с обычным API после добавления административного пространства.
- OpenAPI содержит каждый endpoint, DTO, фильтр, код ошибки и ограничения PATCH. Angular использует именно эту схему.

Операции реализуются в unistay-api, интерфейс — в unistay-admin. На предзащиту 24 октября обязательна базовая Angular-панель на реальном C# API: login, GET admin/me и GET списков users/listings/applications по этим DTO. Её permissions содержит только users.read, listings.read, applications.read. Это D07/Q04/Q05 из плана. Остальные endpoints, permissions и изменения добавляются в V1; полнота спецификации не означает готовность реализации.
